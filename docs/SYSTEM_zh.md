# claude-hub 系统说明

> 本文只讲**结构、功能与思想**，不含任何代码。
> 配图：[`architecture.svg`](./architecture.svg)

---

## 一、这是什么

claude-hub 是一个跑在你自己机器上的**多会话 AI 编码任务中心**。

你本机已经装了 Claude Code 或 Codex 的命令行；它们很强，但一个终端窗口只能盯一件事——
开三个项目就要开三个窗口，任务排不了队，关掉终端就断，出了错只能翻日志，换台电脑就什么都看不见。

claude-hub 在这些命令行**外面**套了一层浏览器界面：

- 多个项目、多个会话，同一个页面里并排管理
- 想到什么先丢进队列，它一条一条排队跑，人可以走开
- 每一步思考、每一次工具调用、每一段耗时，事后都能回看
- 会话记录直接读引擎自己写的文件，终端里跑的历史照样能看见、能续接
- 需要的时候，还能从别的地方远程连回这台机器

一句话：**执行永远在本机，界面只是一个遥控器。**

## 二、七条设计思想

这些是整个系统所有取舍的来源。看懂这七条，后面的结构都是自然结果。

### 1. 不重复造数据源

Claude Code 和 Codex 自己已经把每一次对话完整写在本机文件里了。
hub **不再复制一份自己的会话库**——会话列表就是扫描这些原始文件得到的结果。

由此获得三个别的做法拿不到的好处：

- 你在终端里手敲的会话，在界面里同样能看到、能接着聊
- hub 崩了、删了、换个版本，历史一条不丢
- 永远不存在"界面里的记录"和"真实记录"对不上的问题

hub 自己只额外记两类东西：**它自己标注的**（置顶、收藏、状态、标题）和**引擎不落盘的**（思考正文、任务起止、失败现场）。

### 2. 调度与实现彻底分家（Struct / Realize）

普通代码里，一个函数同时回答两个问题：*这个功能做了什么*，和*每一步具体怎么做*。
这两类知识性质完全不同，混在一起的结果是：想读架构必须穿越细节，想改细节随时误伤架构。

本系统把它们拆成两层：

| | 调度层 | 实现层 |
|---|---|---|
| 回答 | 用了哪些能力？顺序是什么？ | 这一步具体怎么跑？ |
| 内容 | "取数据 → 转换 → 落盘 → 广播" | 解析、循环、错误处理、真实读写 |
| 变化频率 | 低（架构稳定） | 高（细节常改） |
| 阅读价值 | 一眼看懂整个功能 | 只在调试时才需要 |

调度层的每个方法通常只有 5–10 行，每一行配一句"谁提供什么"的注释。
**目标是：不打开任何实现文件，也能完整准确地读懂一个功能如何运作。**

实现层有三条铁律：不新增对外接口、不写调度顺序、不碰别人的边界。
于是"换一种实现"永远不需要动骨架，"调整流程"永远不需要读实现。

### 3. 工具与业务分离

在写任何业务之前先问：能不能抽一个**和业务无关**的通用工具？
先建工具，再用工具完成业务。工具里一旦掺进业务参数，通用性、可解释性、可独立测试性同时下降。

同理，**通讯只管收发，不懂内容**。连接、断开、发一条、收一条、重连——通讯层对消息的业务含义一无所知。
"收到这条消息该做什么"属于业务层。结果是通讯层测通一次，此后再不因业务变化而改动。

### 4. 静默失败是最大的失败

最糟糕的体验不是报错，是**点了没反应**。

系统里凡是可能"悄悄不干活"的地方，都被强制变成可见的：

- 引擎退出码是 0 但从头到尾一个字都没输出 —— 判定为失败，不当成功
- 进程活着但迟迟不吭声 —— 到达阈值就主动往界面推一条"疑似卡住"，并附上排查建议
- 启动阶段就失败（找不到程序、权限被拒、文件类型不对）—— 翻译成人话，连同用的哪个程序、在哪个目录跑、完整命令一起显示
- 任务的失败原因直接摊在正文区，带一键复制，而不是只画一个红点
- 后端级异常除了写日志，还推一条横幅到界面

配套的规矩：**禁止直接打印日志、禁止裸接错误**。所有日志走统一出口（带开关、级别、模块过滤），
所有错误走统一处理器（预留了告警接入点）。这样将来接告警平台只改一处，调用方一行不动。

### 5. 每一步都自己校验

类型检查是编译期的，拦不住运行期的非法状态（空串、负数、外部返回空、AI 回了怪格式）。
所以每个方法入口都做业务级校验，**错误在哪一步发生就在哪一步抛出**，绝不带着非法状态往下传。
报错信息必须包含方法名和那个非法值，让日志直接指向出错位置。

### 6. 拿来就能用，且不偷偷下大东西

安装与自检是**同一套逻辑**：启动脚本会跑一遍完整体检，缺什么补什么，已就绪的部分自动跳过。
Node 不够新就下一份便携版；源码比编译产物新就自动重编；编译万一失败就降级直跑源码并明确提示。

但**体积大的东西一律不预置**：两个 AI 引擎各几百 MB，而多数人本机早就装了。
所以默认只检测和报告，没装的人在引导页点一下即装，且**只装你真正选的那一个**。

选国内镜像还是官方源？**实测，不猜**。你自己配过源就原样用你的；没配过就同时向两边发一次探测请求，谁快用谁——
这比按地区或语言猜准得多（挂着代理的国内机器往往官方源反而更快），选中的源装到一半失败还会自动换另一个重试。

### 7. 跨平台是硬约束

Windows、macOS、Linux 一等公民。凡涉及进程、路径、命令行差异的地方，一律运行时判断分别处理，
禁止把任一平台的假设写死。同一套安装/自检逻辑三个平台共用，各平台的启动脚本只负责"找到可用的运行时"然后调它。

## 三、整体结构

系统由两个相互独立的部分组成：

| 部分 | 角色 | 是否必需 |
|---|---|---|
| **claude_hub** | 主体：本机的多会话任务中心 | 必需 |
| **claude_relay** | 可选：远程访问中继 | 可选，零侵入 |

### 分层（自上而下）

```
使用者（本机 / 局域网 / 经中继的远程浏览器）
        ↓
前端（静态文件，零构建）—— 只渲染、只发请求，不含业务判断
        ↓  REST 请求 ↑ WebSocket 推送
接入层 —— 口令鉴权 → 路由分发 → 托管前端。只转发，不写业务
        ↓
调度层 —— "做什么"：依赖关系与执行顺序
        ↑ 继承
实现层 —— "怎么做"：解析、状态、真实读写
        ↓ 使用
基础设施 —— 纯工具 / 配置 / 类型
        ↓
外部世界 —— 引擎子进程、引擎的原始记录、本地数据目录、内置运行时、外部 API
```

同一层内部还有一条横向规矩：**工具与配置必须和调度层同级，不跨模块共享**。
前端和后端运行环境不同，同名工具的实现可能完全不同；强行共享会让工具变成"环境判断大杂烩"。
真正与环境无关的纯逻辑，由各自的工具在内部引用共享实现，对外仍是各自独立的边界。

## 四、功能地图

### 会话与任务

- **会话管理**：按项目目录组织；也可切到"工作台"视图跨目录平铺所有会话。支持置顶（限量，超出淘汰最早的）、收藏、手工状态标记（活跃 / 待测试 / 已完成）、改标题。
- **全文搜索**：跨会话在标题和全部对话正文里找关键词——因为前端只加载当前打开的那个会话，全文搜索必须由后端逐个读原始记录完成。
- **草稿会话**：新建会话只是一个内存草稿，不落盘、不自造 ID。发出第一条消息后由引擎生成真实 ID，再回写校正，保证 hub 记的 ID 和真实文件名永远一致（否则就会出现"历史查不到"或"列表里分裂成两个"）。
- **任务队列**：一次可以提交多条，全部排队顺序执行。支持停止当前任务（跳到下一条）、暂停整条队列、把某条任务暂定跳过。暂停期间新加的任务算"补充"，会插到最前并允许越过暂停立即执行。
- **重启恢复**：后端重启后把队列载回内存并自动续跑；某个会话的目录被删或异常时只跳过它，不连累其他会话。

### 过程可观测

- **全过程轨迹**：AI 干活的每一步——思考正文、工具入参、工具输出、每步耗时、token 与费用——逐条落盘，事后完整回看。
- **两路数据合并**：一路是 hub 执行任务时实时捕获的（这是**唯一**能拿到思考正文的途径），一路是从引擎自己的记录反推的（覆盖你在终端里手跑的会话）。读取时合并去重：正文类以引擎的官方记录为准，实时流只补它缺失的部分。
- **统计视图**：把"慢在哪"直接算出来——哪个工具最耗时、哪一步等最久。

### 引擎与模型

- **双引擎**：Claude Code 与 Codex，会话级别二选一。一旦会话开始即锁定，不允许中途换。
- **服务商切换**：除官方外，支持接入第三方兼容服务商，填入密钥后模型列表实时拉取。
- **模型探测**：不猜，实测。"当前实际生效的是哪个模型"通过真实启动一次引擎读回它自己报告的名字，拿到就立刻结束进程，几乎零开销；"有哪些模型可用"按引擎特性分别处理，可选做一次极小的真实调用来确认可用性。
- **协议转译**：某些服务商的接口形态和引擎要求的不一致时，本地起一个转译代理居中翻译，对引擎完全透明。
- **斜杠命令**：用量查询、上下文压缩等原生命令可以直接在界面里跑，结果作为一次性反馈返回——不进任务队列、不污染对话记录。

### 项目与文件

- **根目录管理**：登记你的项目目录；可新建项目（目录名有规范约束）、加备注和相关链接、标记重点文件夹。
- **文件管理器**：在根目录范围内浏览、预览、编辑、搜索、上传。**所有路径都被强制约束在根目录之内**，防止穿越。
- **项目模板**：新建或选中一个还没有项目说明文件的目录时，引导选一个模板（内置几套，也可指向你自己的模板集合），一键写入。用户明确跳过后就不再问。
- **预设提示词**：设置里写一段全局提示词后，每次发消息前检查当前项目的说明文件，没写过就幂等地写进去。
- **一键推送**：改完直接提交推送。

### 运行环境

这是一个专门的面板，回答四件事：Node、Git、Claude Code、Codex —— **有没有、用哪份、缺的怎么装、装的过程怎么样**。

- 每个工具都可以独立选择来源：**自动**（本机有就优先用本机的，没有才用内置）、只用本机、只用内置。选中的那边缺失时自动回退另一边，面板上会明确标出真正生效的是哪一份。
- Node 和 Git 有内置便携版可下载；两个 AI 引擎不内置，走全局安装（源竞速）。
- 探测失败不吞掉——"文件在但版本号读不出来"正是被安全软件拦截或装坏的典型表现，原因会直接显示出来。
- 偏好一旦改变，子进程的查找路径立刻重组，保证后续启动的引擎命中你选的那份。

### 安全与访问

- **口令**：没有任何内置或默认口令。首次打开界面时你自己设定，以"随机盐 + 哈希"保存在本地，不存明文。改口令后所有已保存的登录凭证立即失效。
- **救急通道**：忘记口令时可以在本机命令行直接重置或清除（能执行本机命令行即视为最高权限），清除后界面回到首次引导状态。
- **引导白名单**：尚未设定口令期间，只放行引导流程必须的少数接口；口令一旦设定立即收紧。

### 体验层

- 中英双语（文案集中在一张语言表里，格式可扩展到更多语种）
- 多套视觉主题
- 样式全部独立成文件，不与结构混写
- AI 回复里如果带了适合可视化的结构化数据，前端自动渲染成图表

## 五、一条消息的完整生命周期

这是理解整个系统最快的路径。

```
你在界面输入 → 入队
      ↓
调度器判断：当前空闲吗？有可执行的任务吗？暂停了吗？
      ↓ 是
准备（顺序至关重要）
   ├─ 定位项目目录
   ├─ 确保预设提示词已写入（失败不阻断）
   └─ 记录任务起点（含完整输入与工作目录）
      ↓
把任务标记为"执行中"（此前所有可能失败的动作都必须已经做完）
      ↓
启动引擎子进程 —— 在项目目录内、用你选定的那份程序、按你选定的模型
      ↓
流式接收，一行一个事件，同时分发到两个去处：
   ├─ 压缩视图 → 实时推送到界面（思考中 / 正在用什么工具 / 输出片段）
   └─ 完整轨迹 → 原样落盘，供事后回看与统计
      ↓
收尾判定
   ├─ 正常完成 → 记录最终回复
   ├─ 有输出但失败 → 带上真实错误、完整命令、工作目录、耗时、处置建议
   ├─ 退出码 0 但全程零输出 → 判为失败（静默失败不放过）
   └─ 启动就失败 → 翻译成人话，同样带完整现场
      ↓
落盘 + 广播 → 界面更新 → 调度器继续下一条
```

**为什么"准备"必须排在"标记执行中"之前**：一旦标成执行中之后才抛异常，队列就会永远停在那里，
界面上的表现就是"发了消息没反应"。顺序本身就是设计。

## 六、数据放在哪

| 数据 | 位置 | 说明 |
|---|---|---|
| 对话记录 | 引擎自己的目录 | **唯一数据源**，hub 只读不改 |
| 思考正文 / 任务起止 / 失败现场 | 本地数据目录 | 引擎不落盘的部分，由 hub 补 |
| 口令（盐 + 哈希） | 本地数据目录 | 不存明文，不入库 |
| 密钥、全局设置、根目录清单 | 本地数据目录 | 不入库，不要打包分享 |
| 日志 | 本地数据目录 | 统一出口，带级别与模块过滤 |
| 内置便携 Node / Git | 独立运行时目录 | 可随时删掉回落到本机版 |

**都在你自己机器上，全程不出网。**

## 七、安全模型（必须明白的取舍）

为了能无人值守地连续执行任务，hub 启动引擎时使用的是**跳过逐次权限确认**的模式。
这意味着一句必须说清楚的话：

> **任何能打开这个界面的人，都能在你的机器上以你的身份读写任意文件、执行任意命令。**

因此系统的默认姿态是保守的：

1. **默认只监听本机回环地址**。"允许局域网访问"是一个需要你显式打开的开关。
2. **绝不要直接暴露到公网**。需要远程时走隧道、VPN、或本仓库的中继方案，并且务必套上传输加密。
3. **口令是唯一挡在任意命令执行前面的东西**，所以要设一个足够强的。
4. 本服务不区分用户——**一个口令即全部权限**。多用户主机上要意识到这一点。
5. 数据目录含会话、密钥与本机设置，不提交、不分享。

## 八、远程访问的做法

中继方案是完全独立的一层，**不改主体一行代码**。

```
浏览器 ──口令──▶ 云端中继 ◀──令牌── 本机 A 的接入端 ──▶ 本机 A 的 hub
                （名册+信使） ◀──令牌── 本机 B 的接入端 ──▶ 本机 B 的 hub
```

三个要点：

- **执行永远在本地**：命令行、登录态、账号全在各自本机。中继只做"在线名册 + 双向转发"，自身不碰任何业务逻辑。
- **接入端主动外连**：本机不需要公网 IP、不需要端口映射，能上网就能接入，天然绕开内网限制。
- **透明代理**：浏览器经中继拿到的就是**原版界面**，页面、接口、实时推送全部照常工作。

中继同样没有默认口令，首次打开当场设定；接入令牌随机生成后打印在服务端日志里。

## 九、这套架构在维护上意味着什么

**读代码时**：想了解一个功能如何运作，只读调度层——它就是一张可执行的架构图，注释和代码传达完全相同的信息。

**改需求时**：改流程只动调度层，改细节只动实现层，两者不会互相误伤。

**换实现时**：从一种存储换到另一种、从一个引擎参数换成另一个，骨架一行不动。

**接告警时**：只改统一错误处理器里的一个钩子，全系统所有调用方零改动。

**加语言 / 加主题时**：文案在一张表里，样式在独立文件里，都不用碰逻辑。

**换平台时**：差异集中在少数几处运行时判断上，不散落在业务里。

## 十、开发完成后的自检清单

每完成一个功能，提交前逐条对照——不符合就先改再提交：

- [ ] 调度层里有没有混进实现细节（错误处理、循环、解析、直接读写）？
- [ ] 实现层里有没有出现"先做 A 再做 B 再做 C"的调度结构？
- [ ] 实现层里有没有偷偷新增对外接口？所有对外接口必须定义在调度层。
- [ ] 工具里有没有掺进业务参数？工具必须与业务无关、可独立测试。
- [ ] 实体里有没有写业务逻辑？实体只该有存取。
- [ ] 每个方法入口有没有校验非法状态？
- [ ] 报错信息有没有包含方法名和非法值，能直接定位？
- [ ] 前端或接入层有没有绕过调度层直接处理业务？
- [ ] 有没有直接打印日志或裸接错误，绕过了统一出口？
- [ ] 有没有写死某个平台的假设？

## 十一、本质

常见的架构模式解决的是"**代码放在哪里**"的问题。

这套框架解决的是"**代码怎么读**"的问题：

> 让"这个功能如何运作"这件事，可以在不打开任何实现文件的情况下，完整、准确地被读懂。

而整个产品解决的是另一个问题：

> 让 AI 干活这件事，从"盯着一个终端窗口等"，变成"排好队走开，回来能看清它做过的每一步"。
